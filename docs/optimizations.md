# 🚀 KopiDB 优化案例

本文记录三项优化：刷盘完成通知减少重复扫描、合并时复用 VLog 引用，以及在首次刷盘和合并时跳过已回滚版本。
每项案例从触发场景出发，说明改动为什么有效、如何验证正确性，以及实测数据能支持什么结论。

## 🔄 刷盘完成通知：调整同一批 ID 的访问方向

### 🎯 场景：数据写完了，完成登记还在反复扫描

普通 `put/remove` 会产生事务完成标记。内存表刷盘成功后，引擎需要把完成的事务 ID 通知事务管理器，
让管理器清理待处理登记并推进连续检查点。大量独立写入会在一次刷盘中产生很多这样的通知。

原来的数据路径是：

```text
SkipList：同 key 的记录按版本降序排列
    ↓ 空 key 的完成标记也遵循这个顺序
MemTable::flush_last：按遍历顺序收集完成 ID，例如 [3, 2, 1]
    ↓ Engine::flush 按 vector 正序通知
TranManager::add_flushed_tranc_id：每次从待处理表开头扫描到目标 ID
```

待处理表按 ID 升序排列。收到 ID 3 的刷盘通知时，管理器可以移除 3，
却不能顺便移除尚未收到通知的已提交事务 1、2：它们的数据可能仍留在其他内存表中。
因此通知顺序为 `3 → 2 → 1` 时，会依次检查 `1,2,3`、`1,2`、`1`。

对于同批连续的 N 个已提交 ID，这部分条目检查约为 `N(N+1)/2` 次。
N 为 100000 时约有 **50 亿次检查**。普通删除事务也属于已提交事务，不能借用回滚事务的提前结算规则绕过扫描。

### 🛠️ 改动：利用已有顺序，从尾部通知

每次 `Engine::flush` 都新建一个空 vector，只接收一张内存表的完成标记。
标记同属空 key，按真实事务版本降序输出，收集过程保序，因此反向访问就能得到升序，无需额外排序。

```cpp
// 节选：其余刷盘、登记和返回逻辑沿用原有流程。
for (auto it = flushed_tranc_ids.rbegin();
     it != flushed_tranc_ids.rend(); ++it) {
  const uint64_t id = *it;
  max_processed_id = std::max(max_processed_id, id);
  if (manager) {
    manager->add_flushed_tranc_id(id);
  }
}
```

现在通知顺序为 `1 → 2 → 3`：较小的已完成项先从待处理表移除，后续通知不再反复经过它们。
改动集中在 [Engine 的完成通知循环](../src/lsm/engine.cpp#L492)，
依据来自 [MemTable 的收集过程](../src/memtable/memtable.cpp#L371)；
[事务管理器的结算规则](../src/lsm/transation.cpp#L1155)保持不变。

| 环节 | 改动或保留的行为 | 目的 |
| --- | --- | --- |
| `Engine::flush` | 完成 ID vector 由正向改为反向访问 | 先移除同批较小的已完成项，减少重复扫描 |
| `MemTable::flush_last` | 保留单表收集顺序，成功刷盘后才输出完成 ID | 既提供顺序依据，也避免提前报告完成 |
| `TranManager` | 保留缺口、回滚和连续检查点规则 | 调整通知顺序后，仍正确处理尚未刷盘的事务 |

这个优化只针对**同一批**通知。不同内存表之间仍可能先完成较大 ID，再完成较小 ID；
无须等待所有较小 ID，也无须改变刷盘顺序。
若待处理表中还有其他较小且未刷盘的事务，它们仍可能被扫描，因此不能据此宣称管理器所有操作都变成线性复杂度。
未来若完成 ID 的来源或收集顺序改变，需要重新检查反向访问的前提。

### ✅ 验证：最大完成 ID 不等于连续检查点

只观察耗时下降不足以确认这个改动正确。
[EngineFlushBatchPreservesGapAndRollbackState](../test/test_lsm.cpp#L4598)设置了更有区分度的场景：

1. 最老内存表包含事务 1、3、5 的完成标记；事务 2 仍在较新的表中，事务 4 已回滚。
2. 第一次刷盘返回最大处理 ID **5**，但连续检查点只能到 **1**。
3. 第二次刷出事务 2，检查点才推进到 **5**；回滚名单继续保留，墓碑仍遮住旧值。

另有 [缺口结算与重复通知测试](../test/test_lsm.cpp#L4541)，
验证乱序完成不会跨过缺口，重复通知也不会把检查点拉回旧 ID。
当时定向测试 10/10 通过，受影响的 LSM、Compact、WAL 三个完整目标共 320/320 通过。
这是该次优化的历史验收结果，未与当前测试数量混用。

## 📦 SST 合并：直接复用已有 VLog 引用

### 🎯 场景：大值已经分离，合并时却又复制一份

WiscKey 模式把大 value 放入追加式 Value Log（VLog），SST 只保存 key、真实版本和引用。
当前引用占 **12 B**，布局为 `[offset:8 B][value_size:4 B]`。
这样 SST 合并可以搬动较小的索引记录，减少大 value 随层级迁移而反复重写的成本。

优化前，合并复用了普通查询迭代器：读到引用时先从 VLog 还原完整 value，
随后 `SSTBuilder::add` 把它当作原值，按阈值再次追加 VLog。
读取结果仍然正确，但每次合并都会付出额外的原值读取、追加写入和文件增长成本。

```text
优化前：SST 中的引用 → 读取 VLog 原值 → 归并完整 value
                                         ↓
                              add 再次追加 VLog → 新引用写入 SST

优化后：SST 中的引用 → 归并引用字节及类型标志
                                         ↓
                              add_vlog_ref → 原引用写入新 SST
```

优化后的普通查询仍还原原值；合并仍要处理 key、版本、墓碑与内联小值。
被省掉的是**已有 VLog 值在合并中的重复读取和追加**，并非整个合并过程。

### 🧩 设计：存储字节和类型一起走完整条合并路径

读取方式通过 `ValueReadMode` 显式选择，与版本过滤独立：

| 读取模式 | 对外返回的 value | 主要用途 |
| --- | --- | --- |
| `Query`，默认模式 | 引用还原后的原值，或内联值、墓碑 | 普通查询；关闭 WiscKey 后输出普通 SST 的合并 |
| `Compaction` | SST 实际保存的字节，已有引用保持原样 | 目标仍为 WiscKey SST 的合并 |

只传一段 12 B 字符串还不够。普通 SST 也可能保存恰好 12 B 的用户原值，
不能仅凭长度把它当成 VLog 地址。`SstIterator::is_vlog_ref()`同时检查读取模式、当前位置和源 SST 的 WiscKey 标志，
之后才依据 12 B 编码规则判断类型。

这条规则依赖现有写入约定：WiscKey SST 中，**恰好 12 B 的原值也必须分离**，即使没有超过阈值；
因此该模式中 12 B 存储值明确表示引用。普通 SST 的 12 B 原值仍是原值，进入合并后由目标 Builder 按当前规则处理。
类型标志仅存在于内存，不修改磁盘编码，也不参与 key、版本和来源优先级的排序。

| 模块 | 具体改动 | 目的 |
| --- | --- | --- |
| [BaseIterator、SearchItem、HeapIterator](../include/iterator/iterator.h) | 增加 `is_vlog_ref()`；堆条目保存引用标志，getter 返回当前条目的标志 | value 在堆中重排、推进时，类型仍跟随同一条记录 |
| [SST / SstIterator](../src/sst/sst_iterator.cpp) | `SST::begin`转发读取模式；`update_current/value`按模式选择解引用或保留存储字节；L0 归并保存类型 | 在最早读取位置避免无用的 VLog 访问 |
| [ConcactIterator](../src/sst/concact_iterator.cpp) | 保存模式，初次打开和跨 SST 推进都转发；类型取自当前子迭代器 | 顺序串联多张 SST 时不丢失读取方式和类型 |
| [TwoMergeIterator](../src/lsm/two_merge_iterator.cpp) | 从当前被选中的输入转发类型 | 两路归并输出的 key、value、版本和类型一致 |
| [SSTBuilder](../src/sst/sst.cpp) | 新增 `add_vlog_ref`，与原值入口 `add`共用 `add_stored_entry` | 引用直接入块；Bloom、版本范围、换块与元数据逻辑只维护一份 |
| [Engine 两个合并入口](../src/lsm/engine.cpp#L824) | L0→L1 和更深层合并都按目标模式设置全部输入迭代器 | 两条路径采用一致语义；关闭分离时能还原原值 |
| [Engine::gen_sst_from_iter](../src/lsm/engine.cpp#L918) | 按当前记录类型选择 Builder 入口，保留真实版本及同 key 不拆表规则 | 最终写出时复用引用，防止把引用再次当作原值追加 |

最末端的分流很小，但只有前面的模式与类型传递完整，才能正确执行：

```cpp
// 当前 entry、版本和类型必须在 ++iter 前取得。
const auto entry = *iter;
const uint64_t tranc_id = iter.get_cur_tranc_id();
if (iter.is_vlog_ref()) {
  new_sst_builder.add_vlog_ref(entry.first, entry.second, tranc_id);
} else {
  new_sst_builder.add(entry.first, entry.second, tranc_id);
}
```

`add_vlog_ref`在修改 Block 和元数据前检查 Builder 模式及引用长度，随后直接写入存储字节；
它不读取原值，也不调用 `VLog::append`。

### ⚙️ 边界：目标模式决定如何处理旧引用

| 合并目标 | 已有引用 | 原本内联的原值 |
| --- | --- | --- |
| 正阈值且有可用 VLog | 保留原引用，即使提高阈值后原值已小于阈值 | 超过当前阈值或恰为 12 B 时首次分离；其余内联 |
| 阈值为 0，输出普通 SST | 读取 VLog 还原原值，再写入 SST | 按原值写入 SST |

墓碑始终作为空值内联。两条合并路径都继续使用原有版本、来源优先级和墓碑规则。
引用复用以它们仍指向当前数据库的有效 VLog 为前提；这次改动不搬迁 VLog 记录，也不回收过去已经产生的重复值。
因此，混合负载仍可能因内联值首次分离而增长 VLog，不能把“已有引用不重写”理解为任何合并都零增长。

其中，无 VLog 源句柄测试刻意让意外解引用立即报错，同时用 Query 模式作负对照；

### 📊 实测：引用密集的四张 L0 合并

| 指标 | 同次复测的冻结旧版 | 优化后 |
| --- | ---: | ---: |
| `Engine::flush`耗时中位数 | 3242.424916 ms | 121.305542 ms |
| 最小～最大 | 3240.818500～3249.670291 ms | 120.448292～121.913375 ms |
| 每轮 VLog 文件新增 | 41,200,000 B | 0 B |

在这组负载下，耗时减少约 **96.26%**，旧版与新版耗时比约 **26.73**。
旧版每轮将 VLog 从 41,200,000 B 增长到 82,400,000 B；新版保持 41,200,000 B。

对照于 **2026-11-17**完成，使用相同基准类及公共 helper、macOS arm64、Debug 构建。
负载是 **10000 个 key × 4096 B value、四张 L0 SST、WiscKey 阈值 64 B**。
两版在功能测试结束后串行运行，各预热一轮、正式采样五轮；每轮从同一份未合并输入复制到新目录。

计时区间只包围触发合并的 `Engine::flush`，包含一条 11 B 内联触发记录的固定刷盘开销。
输入生成、目录复制、打开数据库、触发记录的 put，以及全部 key/value/版本校验都在计时外。
没有清空系统缓存，因此不代表冷缓存性能；这也不是纯 compaction 函数计时或事务/WAL 基准。

VLog 数字表示**文件增长量**，不等于物理磁盘 I/O。
这些结果仅支持该引用密集负载下的合并收益，不能外推为整个数据库吞吐量提升 26.73 倍。
数据与 [A15 完成验收记录](../agent/AUDIT.md#a15)及保留的原始前后对照一致，本文未重新运行基准。

<a id="aborted-versions"></a>

## 🗂️ 已回滚版本的刷盘、合并与点查开销

读未提交事务的修改可能已经进了内存表，甚至已经写进 L0，事务才回滚。以 `k100002` 为例，磁盘上可以同时有已回滚的 `@6` 和有效的 `@5`。旧版点查正确地返回 `@5`，但下一次合并还会把两个版本都写一遍。

首次刷盘现在先收集事务完成标记，再逐条检查业务记录，只有需要保留的版本才进入 `SSTBuilder::add()`。因此 WiscKey 模式也能省掉对应的 VLog 追加。已经在 SST 上的记录则在合并的两个输入端通过 BlockIterator 检查，源层和目标层都能跳过已确认回滚的版本。活跃事务、有效历史版本和墓碑继续保留。查询继续检查回滚状态，以处理合并结束后才回滚的事务。

| 合并后分散查询 | 50% | 0.506 µs/次（0.500–0.516） | 0.488 µs/次（0.484–0.513） | -3.53% |

50% 回滚时，两种首次刷盘以及普通合并都从写 20,000 条降到写 10,000 条。普通首次刷盘的 L0 和普通合并的 L1 均从 **3,021,873 B** 降至 **1,530,613 B**。WiscKey 首次刷盘的 L0 从 **699,915 B** 降至 **369,635 B**，VLog 新增量从 **2,900,000 B** 降至 **1,450,000 B**。0% 回滚时，各项输出条数和字节数与旧版相同。

首次刷盘计时只包围一张内存表的公共 `flush()`，L0 起初为空，WiscKey 阈值为 64 B 或关闭。普通合并每轮复制同样的四张 L0、一张 L1 和事务状态文件，只计合并开始到结束标记之间的时间。基准在计时外核对物理记录和真实版本。旧首次刷盘程序取自已有合并过滤、尚未接入首次刷盘过滤的版本；旧合并程序取自两个入口都未接入过滤的版本。

点查走合并后的 `LSMEngine::get(key, 0)`，每轮先预热 10,000 次，再计时 250,000 次单线程命中查询。热点组反复查 `k100002`，分散组按固定顺序查遍所有 key 共 25 遍。50% 组只剩可见的 `@5`，热点查询八对样本均更快，分散查询七对更快。0% 组两类点查在八对中各有七对略慢，但新旧范围有重叠。这里观测到的是预热后的整次点查耗时，无法单凭这些样本归因到锁、推算冷盘 I/O 或给出单次请求的 P95。
