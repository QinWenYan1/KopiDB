# 起草可直接发布的 issue

让没有读过聊天记录的人，也能理解问题、找到对应代码、复现错误并判断修复是否完成。本 skill 负责 issue 内容；问题是否成立由 [verify-before-fix](../verify-before-fix/SKILL.md) 核查，问题登记与状态流转由 [audit-to-plan](../audit-to-plan/SKILL.md) 管理。

## 1. 确认本次要写的问题

- 读取用户指定的问题及 AUDIT 对应条目，沿用稳定编号，例如 A2；核对直接相关的当前代码与已有测试证据，不重新开展全库审计。
- 每进入一个新的修复问题，先在聊天中起草 issue。同一问题内逐函数推进时不重复起草；用户要求改写时更新原草稿。
- 区分已复现缺陷、静态推导的疑点、可选改进和后续 Lab 未实现功能。证据不足就说明待验证，不能写成已确认失败；已修复的问题应标明历史现象与当前状态。
- 复用仍适用的测试记录，注明实际运行结果；历史运行不能写成“本轮重测”。没有相关新改动或疑点时，不为写 issue 重跑整套测试。
- 章节归属遵循项目的目录编号＋名称，必要时补充文章标题和正文小节。例如目录 5.1.2「事务管理器」（文章标题 Lab 5.2）的正文 3.2.3 get；不能与目录 5.2「WAL 和崩溃恢复」混淆。

## 2. 提供 GitHub 上能打开的源码位置

- KopiDB 仓库根地址为 `https://github.com/QinWenYan1/KopiDB/`；其他仓库按用户指定或实际仓库确定，不机械沿用此地址。
- 对外 issue 使用完整 GitHub URL，不能使用 `/Users/...`、`file://`、编辑器链接或只有本机能访问的测试日志路径。链接文字写清函数／测试名，必要时附行号。
- 优先使用固定提交的链接，格式为 `https://github.com/OWNER/REPO/blob/COMMIT_SHA/path/to/file.cpp#L10-L20`，避免后续修改使引用漂移；核对该提交中的实际行号与正文描述。
- 本地 HEAD 不等于已推送的远程提交。优先使用 GitHub 连接工具读取指定提交的文件，确认远程可访问且内容对应；连接工具不具备能力时再用合适的只读方式核实。
- 文件读取接口返回的 `sha` 可能是文件的 **blob SHA**，不能当作提交 SHA 拼入 `blob/COMMIT_SHA/`。提交 SHA 应来自实际提交记录，并通过远程读取验证。
- 如果修改尚未推送，不能把本地修改后的行号套到旧远程代码上。可以引用已核实的远程基线并附相关本地差异片段；只有本地证据时明确说明版本情况，不编造可访问的链接。
- 无法取得固定提交时，可引用已核对内容的远程分支链接，并说明引用分支；无法核实时如实说明，不为制造链接而执行提交、推送或发布操作。
- 测试证据优先链接仓库中的测试函数，附必要的失败输出。临时日志只在本地 AUDIT 中留档，公开正文应能独立说明结果。

## 3. 写成完整、可复制的正文

按复杂度采用以下内容，简单问题可以合并段落，不强行凑章节：

| 内容 | 写什么 |
| --- | --- |
| 标题 | 具体触发或错误行为及影响；已有审计编号时可使用 `[Bug][A2]`。不要只有“修复 get”这类模糊标题。 |
| 问题描述 | 当前发生什么、影响谁；章节或设计约定与判断有关时再补充所属范围。 |
| 复现步骤 | 约定内有效的输入与操作顺序，说明关键条件，如事务创建先后、是否提交、是否刷盘。用最小案例，不依赖聊天上下文。 |
| 预期与实际 | 明确比较同一场景下应返回什么和实际返回什么；多种并列场景可用表格。 |
| 代码位置与原因 | 每个关键原因配对应源码链接，解释它如何造成上述结果；未证实的原因标为推测。 |
| 测试证据 | 具体用例、运行结果和必要的失败输出，区分已复现、仅代码推导及尚待补测。 |
| 建议修复方向 | 最小必要改动与涉及函数，说明需要保留的既有行为；拟新增接口标为草案，不写成已经实现或唯一可行方案。 |
| 验收标准 | 用复选框描述可观察的行为及必要回归，覆盖失败场景和相关正常行为，不只写“代码完成”或“测试通过”。 |

- 使用简明中文，缩写首次出现时说明含义；难点配具体 key、版本号和操作顺序，避免只讲抽象术语。
- 修复建议与事实证据分开，影响和严重程度以证据为依据，不加入未经核实的工期或风险断言。
- 正文不写“你刚才说”“按我们上次讨论”等聊天指代，不复制整份全局计划或无关问题。
- 用户要求可直接 copy/paste 时，最终只给标题与 issue 正文，保留完整 Markdown 链接和验收复选框；不混入整体进度表、工具执行说明、提问或下一步教学内容。
- 仓库或用户提供了 issue 模板时按模板组织，保留上述事实和证据，不以固定格式覆盖用户要求。

## 4. 交付与工作边界

- 交付前核对：编号与范围准确；案例符合现有约定；事实有依据；源码链接与版本对应；验收能判断问题是否解决。
- 默认仅起草，由用户手动发布；本 skill 不授予创建、评论或修改远程 issue 的权限。
- 起草完成不等于已经发布，也不等于缺陷已解决。按 audit-to-plan 更新必要状态，不把文案完成计入功能验收进度。
- 发布 issue 不作为继续实现的前置条件；按用户已有授权和逐函数节奏继续，不增加新的审批门槛。
