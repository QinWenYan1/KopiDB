# 问题先记账，选中再实施

把“发现了哪些问题”和“现在解决哪个问题”分开维护。问题进入 PLAN 表示工作范围发生变化；AUDIT 中的原始记录仍保留，以便追踪依据和最终结果。

## 三份文档的职责

| 文件 | 维护内容 |
| --- | --- |
| [AUDIT.md](../../AUDIT.md) | 全局问题账本：疑点、已确认缺陷、改进建议、证据、优先级及处理状态；包括已经解决的记录。 |
| [PLAN.md](../../PLAN.md) | 当前已选定工作的目标、具体函数、必要联动、实施步骤、TODO 和验收标准。修复任务引用 AUDIT 编号。 |
| [STATE.md](../../STATE.md) | 项目现状、已确认设计、全局约定、Lab 进度及整体排期；问题详情链接到 AUDIT，当前执行细节链接到 PLAN。 |

问题事实以 AUDIT 为准，执行步骤以 PLAN 为准。不要在三份文件中维护同一份完整问题清单。普通 Lab 功能开发继续按既有计划推进，不必为了使用本 skill 先制造问题条目。

## 发现时登记

- 先核对已有编号、位置和触发场景；重复发现合并进同一条记录，补充证据，不重复计数。
- 使用稳定且不复用的编号，沿用本项目 A1、A2 等编号。标题或代码位置变化不改编号。
- 条目至少说明：问题是什么、属于疑点／缺陷／改进建议中的哪类、当前状态、相关文件与函数、触发场景、预期与实际差异、现有证据和影响。资料不足就标明缺少什么。
- 是否成立、是否必须修改，按 [verify-before-fix](../verify-before-fix/SKILL.md) 核查。未经验证的猜测标为“待确认”，不与已复现 bug 混报。
- 后续 Lab 正常尚未实现的功能属于 STATE 的整体排期，不列为已完成模块的 bug。已接受的设计限制也不能仅因存在限制就升级为必修缺陷。
- 优先级依据影响，改动规模依据修复范围。需要估时时说明依据和不确定性；方案未定时不要把粗估累计成确定的总工期。

## 选中后进入 PLAN

- 用户已经决定处理某项问题，或已有明确授权覆盖该修复时，将其作为当前工作写入 PLAN；已有授权无需再次确认。
- PLAN 保留编号和 AUDIT 链接，简述目标，展开具体函数、必要联动、顺序、验收标准及不包含的工作。用 [goal-to-plan](../goal-to-plan/SKILL.md) 拆解，不复制整份审计报告。
- 同步把 AUDIT 的条目标为“已纳入计划”，附当前计划链接；开始实施后改为“处理中”。不要物理删除原条目，也不要把未选中的问题都变成当前 TODO。
- 实施中发现新问题，先回 AUDIT 记账。只有确属当前目标的必要依赖，才说明原因并补入当前 PLAN；其他问题留待排期。遵守用户已明确的主线与授权范围。
- 继续任务时优先读取 PLAN 引用的条目，按需要查看全局索引，不因本 skill 自动重新审计全库。

## 验收后回写

- 代码写完但尚未验证时标为“待验收”；满足既定验收标准后，才在 AUDIT 标记“已解决”。
- 记录简短修复结论、解决日期及实际验收证据，可引用测试名、日志或已有提交；不把未运行、失败或依赖未实现功能的测试记作通过。
- PLAN 更新对应步骤；一轮工作结束时，将项目层面的结果归入 STATE，再清理已完成的执行计划。AUDIT 的编号、问题依据和解决结果继续保留。
- 清理或替换 PLAN 时，移除已结束条目的“当前计划”关联，保留其修复结论和验收证据，避免旧问题的链接以后指向另一轮任务。
- 已解决问题再次出现时，重新打开原条目并追加复现依据；若根因确实不同，再创建关联的新编号。
- 误报可标为“已排除”并说明依据；决定暂缓时记录原因。不要靠删除条目，让未解决的问题从账面上消失。

常见状态流转：**待确认 → 待排期 → 已纳入计划 → 处理中 → 待验收 → 已解决**。已有充分证据可直接登记为待排期，无需为了流程补造中间步骤。

例：A1 已复现但未选中，留在 AUDIT 待排期；用户要求开始修 A1 后，PLAN 展开它的函数和测试，AUDIT 更新状态；验收通过后回写 A1 的结果。A2～A4 不因 A1 开始修复而自动进入本轮计划。
