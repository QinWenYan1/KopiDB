# 逐函数完成 Lab

目标：按 Lab 主线完成可解释、可验证的实现，同时让用户理解并亲手写出业务代码。**逐函数推进，不等于逐函数孤立设计。**

本 skill 管理教学与验收流程。判断疑似 bug、设计状态或参数传递、审查修复必要性时，同时使用 [verify-before-fix](../verify-before-fix/SKILL.md)，不重复维护其详细核查规则。

## 1. 先读资料，确定本轮范围

- 新目标与阶段拆解使用 [goal-to-plan](../goal-to-plan/SKILL.md)；已有确认结果直接沿用，再按本 skill 逐函数推进。
- 先读项目 [AGENT.md](../../../AGENT.md)、[STATE.md](../../STATE.md) 和 [PLAN.md](../../PLAN.md)，核对当前代码与记录，沿用用户已经确认的设计。
- 开始新一节时阅读对应 Lab，提取要求实现的函数和行为；继续已有任务时复用已读资料，按需要核对相关章节，不每轮从头探索。
- Lab 指定实现的函数，无论骨架是否挖空，都要独立推导并实现；不能把现有函数体直接算作我们已经完成的任务。
- 新计划列明阶段、函数顺序、必要依赖和具体行为验收标准，按用户要求先给方案审阅。只有已确认的当前工作进入 PLAN；问题详情留在 AUDIT，整体排期与全局约定放 STATE。
- 确定任务目标和范围时就列出具体函数名、所在文件及职责，区分独立实现、必要修改和仅联动复核，不能只说“完成状态维护”等模块目标。拟新增接口明确标注为草案，名称与签名未定时如实说明；不把复核名单算成必改名单。

## 2. 先理清相关设计，再拆成函数

- 在给出第一个函数前，检查本次功能直接涉及的调用链，明确输入输出、状态由谁维护、谁创建和使用对象，以及已有锁和生命周期约定。
- 提前识别必须联动的声明、构造函数、调用方及测试，让用户知道修改范围；不写完一个函数才不断追加本可预见的依赖。
- 只检查当前功能需要的路径，不借整体设计之名开展全库审计。状态归属与参数传递的具体检查遵循 verify-before-fix。

## 3. 独立推导，再对照作者

- 先根据本地接口和已确认的语义推导方案，再对照 Lab 与作者参考，分别说明文档要求、参考行为、本地约定和自己的判断。
- 参考方案适合本地设计时可以采用，解释关键理由即可；不为了与作者不同而增加复杂度。参考实现有缺陷时，用具体路径和行为说明差异。
- 核实参考来自哪个文件或版本；资料不可用、代码仍是桩或结论未验证时明确说明，不把猜测写成作者原意。

## 4. 一次讲清一个函数

- 先说明函数做什么、输入输出、谁调用它，以及它解决当前目标中的哪一步。
- 给出准确文件、函数名和当前行号；在聊天中提供完整函数实现。必要的头文件声明、成员和调用方修改也要精确列出，避免“原循环之后加上”这类定位。
- 写中文注释，解释关键条件为什么存在、状态变化和处理顺序；难点配一个小例子，不仅翻译代码语句，也不把讨论历史塞进注释。
- 使用简明中文，先给结论再展开一个难点；用户理解有误时指出具体原因，不为附和而改变判断。
- 业务源码及头文件由用户手动修改，除非用户明确授权代改。助手可以按授权补测试、维护文档和运行检查。

## 5. 检查用户实现并做必要验证

- 用户写好后重新读取当前代码，检查行为与接口契约，不要求逐字照抄草案。已经合理的实现不因风格偏好返工。
- 根据已确认需求补充有意义的场景测试，说明各用例的目的；运行与本次改动相关的构建和测试。项目测试可能清理数据，须在独立临时目录准备配置，以绝对路径运行测试程序。
- 报告实际运行范围、通过与失败数量，以及尚未验证的部分。仅静态检查、仅构建和运行测试分别说明；局部通过不能推导整个模块完成。
- 依赖尚未接通时明确标记待验收。按已确认排期暂缓测试时保留用例、失败依据和恢复条件，不把暂缓计为通过，也不为通过而削弱有效断言。
- 检查通过后，只有用户授权继续才进入下一函数；“检查没问题就下一个”已经包含授权，无需再次询问。没有新改动或失败线索时，不重复扩大测试；纯注释修改无需重跑业务测试。

## 6. 发现问题先分类，守住 Lab 主线

- 区分当前功能必需的修复、可选防护、后续优化和其他 Lab 任务；判定依据与证据要求使用 verify-before-fix。
- 当前验收被必要依赖阻碍时，说明具体原因和最小联动范围；新发现先登记 AUDIT，按 [audit-to-plan](../audit-to-plan/SKILL.md) 决定是否进入当前计划。其他问题不自动插入当前步骤；后续 Lab 的正常未实现功能继续留在 STATE 排期。
- 每进入一个新的修复问题，按 [draft-issue](../draft-issue/SKILL.md) 先在聊天中交付 issue 草稿，由用户手动发布，再按已有授权逐函数推进；同一问题内不重复起草，不把普通 Lab 新功能强行包装成 bug。
- 不把助手额外设计的接口约束当成需求，再用自己编写的测试证明用户实现错误。

## 7. 展示进度并完成收尾

- 展示计划或进度时列出当前 PLAN 的全部阶段及状态，标明当前函数，附完成百分比。默认按“验收通过的阶段数 ÷ 总阶段数”计算，说明口径；阶段内部分完成不折算，也不表示工时比例。
- PLAN 只保存当前任务、顺序、TODO 和验收标准；AUDIT 保存问题事实、处理状态与解决证据；STATE 保存项目现状、已确认设计及整体排期。实现检查与测试验收分别记录，避免把一个函数通过写成整个阶段完成。
- 收尾时核对范围内实现、必要回归、旧注释和已知限制；明确哪些能力已经验证，哪些仍依赖后续任务。
- 本轮完成后，在 AUDIT 回写相关问题状态和验收证据，向 STATE 记录项目层面的结果，再清理旧 PLAN。未选中的问题继续留在 AUDIT；下一节按用户授权开始，不因本轮完成就自动扩展任务。
