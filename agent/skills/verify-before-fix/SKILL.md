# 先验证，再修复

目标：找出当前任务中有证据的正确性问题，先理清相关职责，再给出必要且范围明确的修改建议和实现草案。

## 检查方法

- 先确认当前任务、用户已接受的设计和本轮范围；教学项目还需确认所在 Lab。已有函数体不等于已验收，也不等于需要重写。
- 独立阅读目标函数及相关调用链，弄清输入输出、调用方保证和下游已有处理；只扩展检查与疑点直接相关的位置。
- 区分内部候选、回调输入和最终用户结果。某层没有过滤，不代表最终结果错误；某层无需过滤，也不能推出其他层都无需过滤。
- 再对照相关接口文档；教学项目同时对照对应 Lab 和作者参考，校正理解。分别说明文档要求、参考行为、本地约定及自己的推断；参考实现可能有遗漏，差异本身也不能证明本地实现有错。资料无法取得时说明限制。
- 判定 bug 前给出约定内可发生的输入或操作顺序、准确代码位置，以及预期与实际行为的差异。代码推演或针对性测试均可作为证据；未证实的疑点标为待确认。
- 问题登记、选入计划和验收后的状态回写遵循 [audit-to-plan](../audit-to-plan/SKILL.md)。本 skill 负责核查依据，不因确认一个问题就自动扩大当前修复范围。

## 给出实现草案前

- 逐函数教学是讲解和落地的节奏，不是孤立设计每个函数。先检查本次功能涉及的调用链，明确“谁提供条件 → 谁保存 → 谁使用”；涉及迭代器时连同构造、定位和推进一起考虑，只检查直接相关路径，不因此扩展为全库审计。
- 明确状态所属对象、初始化位置和允许改变它的操作。对象已保存的配置，后续操作优先复用；让普通操作额外接收参数并覆盖成员，需要具体调用需求。尤其检查默认参数是否会意外清空已有配置。不要把本次经验扩大为“所有配置只能在构造时设置”。
- 区分同一对象重复配置与跨对象传递依赖：创建新对象时仍可能需要提供配置；不能因为下游类有同名成员，就删除必要的构造参数。
- 提前列清必须联动的声明、调用方和测试，检查已有成员或机制能否复用。保持逐函数推进，但在用户开始手写前说明必要联动，避免写完后才不断追加本可预见的改动。

## 修改与验证边界

- 明确区分：必修 bug、完成当前功能的必要改动、可选防护或后续优化。检查不加新判断时，现有调用链能否已保证正确性；不要把接口偏好直接称为 bug。
- 可选防护不自动加入当前修复清单；风格偏好、假设未来接口变化和违反既有约定的调用，不能直接作为当前代码错误的证据。
- 优先最小必要改动。已有实现满足要求时明确说无需修改；不为减少几行代码来回推翻已经合理的选择。
- 测试预期来自接口承诺和已确认需求，不能先擅自增加要求，再用测试失败证明有 bug。发现测试预期错误时，说明依据后修正；不能为通过测试而删除有效断言。
- 助手编写的测试不能单独证明旧设计必须保留。接口语义调整时先核对实际调用方和兼容要求；按已确认的新语义迁移测试，保留仍适用的正确性与异常覆盖，不为维护自己的旧测试而增加无需求的接口能力。
- 运行与改动相关的必要检查，区分实际测试结果与静态推断，不把局部通过说成整个模块完成。
- 遵守当前协作方式；用户约定手写业务代码时，在聊天中给出实现，不代改源码。测试和文档按已有授权处理。

## 对用户说明

- 先给结论，再用准确位置和必要的具体例子解释。涉及接口或职责调整时，简要交代“为什么必须改、已有机制能否复用、哪些地方必须联动”，不为简单改动增加冗长流程。
- 用户质疑设计时，先简短复述其指向的具体行为，再核对当前代码。不要抓住命名或笔误反复解释，也不要未核对就为旧方案辩护；证据不足时明确说明。
- 确认此前判断有误时，指出错误前提并纠正相关记录，不以新增假设维持原结论；局部发现也不能直接推广为其他模块都有同类问题。说明验证范围，不确定就直说。
