# 先验证，再修复

目标：找出当前任务中有证据的正确性问题，给出必要且范围明确的修改建议。

## 检查方法

- 先确认当前任务、用户已接受的设计和本轮范围；教学项目还需确认所在 Lab。已有函数体不等于已验收，也不等于需要重写。
- 独立阅读目标函数及相关调用链，弄清输入输出、调用方保证和下游已有处理；只扩展检查与疑点直接相关的位置。
- 区分内部候选、回调输入和最终用户结果。某层没有过滤，不代表最终结果错误；某层无需过滤，也不能推出其他层都无需过滤。
- 再对照相关接口文档；教学项目同时对照对应 Lab 和作者参考，校正理解。分别说明文档要求、参考行为、本地约定及自己的推断；参考实现可能有遗漏，差异本身也不能证明本地实现有错。资料无法取得时说明限制。
- 判定 bug 前给出约定内可发生的输入或操作顺序、准确代码位置，以及预期与实际行为的差异。代码推演或针对性测试均可作为证据；未证实的疑点标为待确认。

## 修改与验证边界

- 明确区分：必修 bug、可选防护、后续优化。检查不加新判断时，现有调用链能否已保证正确性。
- 可选防护不自动加入当前修复清单；风格偏好、假设未来接口变化和违反既有约定的调用，不能直接作为当前代码错误的证据。
- 优先最小必要改动。已有实现满足要求时明确说无需修改；不为减少几行代码来回推翻已经合理的选择。
- 测试预期来自接口承诺和已确认需求，不能先擅自增加要求，再用测试失败证明有 bug。发现测试预期错误时，说明依据后修正；不能为通过测试而删除有效断言。
- 运行与改动相关的必要检查，区分实际测试结果与静态推断，不把局部通过说成整个模块完成。
- 遵守当前协作方式；用户约定手写业务代码时，在聊天中给出实现，不代改源码。测试和文档按已有授权处理。

## 对用户说明

先给结论，再用准确位置和一个具体例子解释。说明是否必须修改、最小改法和验证范围；不确定就直说。确认此前判断有误时，指出错误前提并纠正相关记录，不以新增假设维持原结论。
