# 先定目标，再拆阶段

先确定完成后应得到什么，再安排到达目标的步骤。发现更多可做的事情，不等于它们都属于本轮任务。

## 1. 核对需求与现状

- 阅读用户要求、相关文档及直接相关代码，分清明确要求、必要依赖和可选优化。
- 修复任务读取 AUDIT 中选定的条目，沿用编号；问题流转按 [audit-to-plan](../audit-to-plan/SKILL.md)，不把全局账本全部搬进当前计划。
- 不把已有待办全部并入新任务，也不把需要检查的函数全部列成必须修改。

## 2. 先确定目标

- 说清要解决的问题、具体函数或产物、完成标准，以及本轮范围边界。
- 涉及代码时给出函数名和文件位置，区分独立实现、必要修改和仅联动复核。
- 拟新增接口标为草案；未确定的名称或行为如实说明。
- 用户要求先审阅目标再审阅步骤时，按此节奏推进。已经确认的目标和已有授权直接沿用，不重复询问。

## 3. 再拆实施阶段

- 先检查相关调用链，再按依赖关系安排顺序；每阶段列出具体函数和实施步骤。
- 提前识别必须共同确定的设计，例如写入与读取使用的文件格式，避免实现后反复追加可预见的改动。
- 阶段数量由任务决定，每阶段都应直接服务于已确认目标。
- 展示阶段、具体工作、验收标准和状态；逐函数落地时仍保持对整体设计的理解。

## 4. 给阶段配验收标准

- 使用可观察的行为和对应验证方式，不能只写“代码完成”。区分代码检查、构建通过、测试通过和完整调用链验证。
- 依赖未完成的功能标为待验收，不能算作通过。
- 展示全部阶段及完成百分比，并说明计算口径；KopiDB 默认按验收通过的阶段数占比计算，不代表工时比例。

## 5. 执行时守住目标

- 已确认的目标、阶段、TODO 和验收标准写入 PLAN；问题事实与处理状态留在 AUDIT；项目现状、全局约定和整体排期留在 STATE。
- 发现新问题先判断是否影响目标。必要联动说明原因和影响后更新计划，可选优化不自动加入；也不能为了显得改动少而隐瞒必要工作。
- 全部阶段通过后，回头核对是否达成最初目标，不能仅凭清单勾完或部分测试通过提前宣布完成。

Lab 的逐函数讲解与实施使用 [lab-workflow](../lab-workflow/SKILL.md)；疑似 bug 与修改必要性的证据核查使用 [verify-before-fix](../verify-before-fix/SKILL.md)。
